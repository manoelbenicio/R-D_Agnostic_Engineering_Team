# ORQ-32 — Gate0 delta: closure and dual-token factual audit

**Mode:** READ-ONLY. No secret value, secret store, DB, runtime, board,

## Verdict

The existing closure audit is directionally correct: ORQ-32 is a false-positive
handshake/rev premise and should be closed as `cancelled`/non-defect, not
`done`. The factual correction that must remain attached is that the product
has two distinct opaque token paths, not one “dual-token handshake”:

- `mdt_` daemon token: generated by `GenerateDaemonToken`, validated by
  `DaemonAuth` and its daemon-token store/cache.
- `mat_` task token: generated by `GenerateAgentTaskToken`, bound to a task,
  injected as `MULTICA_TOKEN`, and validated through the regular task-token
  path (`GetTaskTokenByHash`), not the daemon-token persistence path.

The prior discovery map's wording that `mat_` uses the same `DaemonAuth`/PAT
cache is factually wrong and must not be reused. The independent closure audit
already records this as E1. Likewise, `mdt_` emission is not proven as a
currently wired production flow; schema/validator/cache exist, while callers
are absent in the inspected product code.
